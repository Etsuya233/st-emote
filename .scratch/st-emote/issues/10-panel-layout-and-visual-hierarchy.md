# 10 — 面板观感：让它在窄栏里也站得住

**What to build:** 设置面板现在把一行的东西硬塞进一行的宽度,按钮换行成三四行、输入框里的标签和描述被截断成「a cute small」「测试表情,详」。这一票只改**版式与视觉层级**:不新增设置项、不改任何规则、不改文案的意思。用户点到的还是同一批控件、同一批字段、同样的行为。

**Blocked by:** 07 — 调试工具、操作入口、本地化与文档;08 — 设置项(面板上现在多了间隙、形态开关与总开关,版式要按最终控件数设计)

**Status:** ready-for-agent

## 现状:照着这张截图诊断

用户提供的真实面板截图(ST 扩展面板,窄栏,深色主题)暴露的问题,按严重程度:

1. **按钮被挤成多行方块。**「render the current chat」占四行、「Add image URL」三行、「Upload images」两行、「Export .zip」「Delete pack」各两行。按钮的 `menu_button` 尺寸跟着文字换行走,于是整行高度被最矮的那个撑成参差的一排。**这是最伤的一条**——一排动作按钮里有一个换行到四行的,整排就散了。
2. **表情包的表头是一整排等权元素。** 封面、包名输入框、「2 stickers」、「Upload images」、「Add image URL」、「Export .zip」、「Delete pack」七样东西同一视觉权重平铺,没有主次。用户看不出哪个是包名、哪个是计数、哪个是危险操作。
3. **单张表情的一行被截断。** 复选框、缩略图、标签输入框、描述输入框、投放方式下拉、「Replace」、「Delete」七样平铺,于是「a cute small」「a default av」「测试表情,详」三个输入框全部显示不全——**而这三个字段恰恰是用户最需要读写的**。描述比标签宽(现有 CSS 是 `flex: 2` vs `flex: 1`),但在这么窄的栏里这个比例救不了任何东西。
4. **作用域三连与「Select all」各占一整行。** 三个作用域复选框和「全选」挤成两行,右侧留下大片空白,而下面的表情行却挤得放不下字。**空间分配正好是反的**:最不需要空间的占了最多垂直空间。
5. **没有视觉分组。** 面板从上到下是一条等密度的流,用户扫一眼分不出「这是设置」「这是工具」「这是数据」。唯一有边框的是每个包。
6. **调试区那两个按钮被拉成两个又高又窄的方块**(截图最上方),因为 `.st-emote-debug-actions` 是 `flex-wrap: wrap` 而栏宽不够。

## 这一票要做什么

### A. 动作按钮的排版律(优先级最高,单修这一条就解决一半问题)

**动作按钮的文字永远不换行。** 给包头与表情行的动作按钮套一个类:`white-space: nowrap`,`flex: 0 0 auto`。按钮宁可自己横向滚动或换到下一行,也不要内部换行成方块。

**动作成组,不逐个平铺。** 一个包的四个动作(上传 / 外链 / 导出 / 删除)收进一个动作区,区本身是 `flex-wrap: wrap` 的容器——区换行是可以的,按钮换行不行。「删除包」与其它三个之间要有视觉间隔(用 `gap` 或一个分隔元素),因为它是不可逆的那一个。

### B. 表头的层级

给包头一个明确的顺序与权重:封面(最左,固定尺寸)→ 包名(可伸展,主)→ 计数(次要)→ 动作区(右,次要)。计数与状态徽章用更弱的视觉(现有 `st-emote-pack-count` 已经是 `opacity: 0.7`,沿用)。**包名输入框是这个包里唯一的主控件**,给它最多空间。

### C. 表情行的重新分组(优先级第二)

一行的七样平铺在窄栏里必然失败。改成两行:

- **第一行**:复选框、缩略图、**标签**输入框(伸展)、投放方式下拉。
- **第二行**:**描述**输入框(通栏),以及「Replace」「Delete」。

描述是第二行,是因为它最需要宽度——用户写的描述往往是一句话,截断成「a cute small」等于没写。标签在第一行是因为它是**标识**,必须一眼可见;描述是**内容**,可以往下沉一行。

缩略图与复选框保持在第一行最左,它们的宽度是固定的,不能被挤。

### D. 作用域与「全选」

三个作用域复选框和「Select all」收进**同一行**的容器(`display: flex; flex-wrap: wrap; gap`),让它们共享剩余宽度,而不是各占一行。作用域是**启停**、全选是**批量操作**,两者视觉上可以同属一行但要有一点间隔。

### E. 版面节奏

- 包与包之间、包与面板顶部的设置之间的垂直间距目前是同一档(`margin-bottom: 8px` 一路用到底)。给**区块之间**一个更大的间距(比如 12–16px),给**区块内部**保持 8px,让版面有呼吸。没有节奏,所有东西看起来就是同一堆。
- 面板顶部那一大段(总开关、两个形态开关、标签名、投放方式、两套尺寸集)目前是一列等密度控件。给它们**分组**:「处理」组(总开关 + 形态开关 + 用户消息)、「标记」组(标签名)、「外观」组(投放方式 + 尺寸集)。分组可以只用间距和一条细分隔线,不必加卡片——ST 的面板里卡片套卡片会显得重。
- 调试区那两个按钮:套上 A 的 nowrap 律即可,顺带把 `.st-emote-debug-actions` 的按钮也纳入同一套动作按钮类,这样三处动作区共享一套外观。

### F. 面板的骨架宽度假设

`style.css` 里的 `.st-emote-*` 规则是照桌面宽度写的(票 07 的遗留待办里点名了这一点)。这一票要把它们改成**在窄栏里成立**:所有固定像素宽度(`6em` / `10em` / `40px` 缩略图)要么改成 `max-width` + `min-width: 0`,要么改成容器查询/`clamp()`。**核心是给 flex 子项加 `min-width: 0`**——这是输入框在 flex 行里被截断而不换行的直接原因,也是最常见的一条修法。

## 明确不做

- **不新增、不删除、不重命名任何设置项、按钮或文案。** 控件集合与票 08 结束时完全一致。若发现某个字段确实没地方放,记进 Comments 而不是当场加字段。
- **不改任何行为。** 点击、校验、保存、重渲染的时机与现在完全一样。
- **不引入依赖、不引入构建步骤。** 扩展仍然是被 ST 当静态站点加载的三个文件。
- **不改 i18n 文案的意思。** 版式改动不需要新的句子;如果为了说得清而要加(比如一节标题),中英两份一起加,并说明为什么必须有。

## 测试

面板的版式**大部分是 CSS,jsdom 测不了视觉效果**。能测的和不能测的要分清,不要用测试假装覆盖了观感:

- **能测的**:动作按钮带 nowrap 类(断言类名);表情行确实分成了两行(断言结构:第一行含标签输入框、第二行含描述输入框);作用域与全选在同一个容器里(断言父子关系);控件集合与改动前**完全一致**(这是最重要的一条回归——用一份 id/class 清单把当前面板快照下来,版式改完必须一模一样);新增的任何 class 都有对应的 i18n 无关的纯样式规则存在。
- **不能测的、留在待人工验收的**:实际观感、按钮在真实主题下的对比度与 hover 态、窄栏与宽栏两端的换行行为、ST 自己的 `.menu_button` / `.text_pole` 覆盖了我们哪些规则。

**把当前面板的控件清单写成一条测试**,是这个票最值钱的东西:它保证这是一次纯版式改动。

## 留给后续 Ticket

- **`st-emote-*` 规则在真实主题下的对比度**:这一票只管排版不管配色。深色主题下 `opacity: 0.7` 的次要文字是否还读得清,是另一件事。
- **窄屏 / 移动端**:ST 的移动布局与扩展面板在窄屏上的表现,本票只按「窄栏」做,没有为手机设计。

## 已知取舍与偏差

- **纯 CSS 为主,DOM 结构要动。** 「描述移到第二行」和「动作收进一个区」都不是纯 CSS 能做的(需要改 `adapter/ui.js` 里的元素树),所以这一票**会动 `adapter/ui.js` 与 `adapter/sizing-panel.js`**。判据是那条控件清单测试:DOM 可以重组,但控件集合一个都不能变。
- **用间距和分隔线分组,不用卡片。** ST 自己的扩展面板里已经有一层卡片(`inline-drawer`),再套一层会让面板变成俄罗斯套娃。分组的表达力靠垂直节奏和一条细线就够了。
- **不碰 i18n 文案。** 如果真机上发现某个按钮标签太长导致排版难看,**那是文案问题,应该在文案里解决**(中英两条一起),而不是在 CSS 里硬压。记进 Comments 等人决定,不要在版式票里偷偷改句子。
- **这一票没有可自动化的验收主体。** 与票 01–09 都不同:那些票的「对不对」能被测试说清楚,这一票的「好不好看」不能。所以控件清单测试是**唯一的硬保证**,其余全靠待人工验收那条列表兜底——别把覆盖率数字当成这票做得好不好的证据。

# 02 — 规则完整：语法、约束、处理范围

**What to build:** 标记的写法和输入规则按规格收口。用户能用两种标记形态、能在多包与单包下都写对名字；会破坏语法的输入在填写时就被拦下；不该被渲染的地方（代码块、系统/旁白、思考链、用户消息）保持原样。

**Blocked by:** 01 — 闭环：一张表情能在消息里出现

**Status:** resolved

- [x] 多个包同时启用时 `[[sticker:包名:标签]]` 正确命中；只启用一个包时，裸标签 `[[sticker:标签]]` 与带前缀写法都能命中；多包时裸标签算未命中
- [x] `<sticker>…</sticker>` 形态可用：在用户的 HTML 转义开关打开与关闭两种情况下都能渲染；标签名可配置，配置成真实 HTML 标签名时被拒绝
- [x] 标签超长、含 `[` `]` `<` `>`、描述换行、包名含 `:` 时，输入被拦下并说明原因
- [x] 同一个包内两张表情同名被拦下；新建或改名导致包名全应用重复被拦下（不自动加后缀）
- [x] 没填标签的表情不出现在清单里、不参与匹配，界面上标为「待填标签」；描述允许留空，界面显示为「—」
- [x] 代码块与行内代码里的标记不渲染；用户消息默认不渲染（有开关可打开）；系统/旁白消息与思考链不渲染
- [x] 同一条消息里同一个标记出现两次就出现两张图

## Comments

- 2026-09-28：已实现。纯核心测试 72 项通过（从 38 项增加到 72 项）。
- 新增 `core/constraints.js`：标签 / 包名 / 描述 / HTML 标签名的字段校验（码点计数、字符约束、单行），以及包名全应用唯一、同包标签唯一这两个领域规则的查重函数。
- `core/token.js` 支持两种形态：`[[sticker:...]]` 与 `<标签名>...</标签名>`，后者同时匹配原样的与 HTML 实体转义后的落地形态；标签名可配，非法或与真实 HTML/SVG/MathML 元素同名时回退为默认 `sticker`。
- `core/render.js` 的 HTML 扫描改为「标记与标签一起走」，因此原样的 `<sticker>…</sticker>` 不会被误当作真实元素跳过，`<code>` / `<pre>` 里的两种形态都保持原样。
- `core/effective-set.js` 现在只把「有标签」的表情放进生效集：没填标签的表情既不参与匹配，也不会进入清单的数据源（清单正文由票 03 生成）。
- 适配层：面板新增 HTML 标签名与「用户消息也渲染」两个开关；包名可改名（改名前查重、改名时同步全局启用引用并提示旧标记失效）；标签 / 描述改动在输入时校验并拦下；未填标签的行显示「待填标签」，空描述显示「—」。
- 「HTML 转义关闭」时，原样 `<sticker>` 会被 ST 的 DOMPurify 清掉，因此适配层注册了一个 `uponSanitizeElement` 钩子放行当前配置的标签名，DOM 路径再按元素处理这一形态。
- 命名说明：面板其余文案仍是英文，票 07 统一做中英双语；本次只按票据原文加入了「待填标签」这一处中文标记。

### 结论

01 与 02 覆盖了 spec 中属于这两张票的全部规则：扩展骨架与闭环、两种标记形态（原样与转义）、单包 / 多包命中规则、重复标记、字段约束与唯一性、代码块与处理范围、未命中处理。裸核心测试 72 项通过，spec 的解析边界在此逐条复核过（空生效集全部未命中；引用块 / 列表项 / 表格单元照常渲染；半截标记保持原样）。

下面把 spec 里**尚未实现**的功能按后续票据归档，供后续票据直接照着做；末尾是当前没有任何票据认领的条目。

### 03 — 生效集与宏

- 角色层（写进角色卡）与聊天层（写进聊天元数据）额外启用表情包；生效集 = 三层并集、按包去重；纯并集，没有排除 / 覆盖 / 优先级（spec「生效集与作用域」、领域模型 #6）
- 群聊里每条消息按该条消息作者所属角色卡解析（spec「生效集与作用域」；user story 30）
- 角色卡引用了本地没有的包 → 界面显示「缺失的包」清单，并可一键导入（spec「生效集与作用域」；user story 29）
- 宏 `{{st-emote}}`（默认等同 `::full`）、`{{st-emote::simple}}`（只列标签）、`{{st-emote::full}}`（每行 `包名:标签`）；清单永远不含描述（spec「提示词：宏」；user story 33–40）
- 生效集为空 → 展开成一个「无」字；启停变化后下一次构建提示词时清单即更新（spec「提示词：宏」）
- 清单文案跟随 ST 界面语言；面板里给出宏的用法示例（spec「提示词：宏」「管理界面」）
- 扩展不向提示词写入任何内容（spec ADR-0004；user story 33）
- 收口清单的**数据源**：直接用 `core/effective-set.js` 的 `packs`（票 02 已保证其中只含「有标签」的表情），不要另行过滤

### 04 — 投放方式与尺寸

- 三种投放方式：原地 / 块后 / 消息末尾；块后的落点取最近的块级容器（段落 / 列表项 / 引用块 / 标题 / 表格单元），断行不算块（spec「投放方式与尺寸」）
- 逐表情覆盖投放方式；覆盖后同时切换尺寸配置套（spec「投放方式与尺寸」）
- inline / block 两套尺寸（最小 / 最大宽高 + `cover` / `contain` / `fill`），`em` / `px` / `%` 手打并原样交给 CSS（spec「投放方式与尺寸」）
- 非法尺寸值当作未设置，并在输入框旁给出可见提示，不阻止继续编辑（spec「投放方式与尺寸」）
- 默认值：inline 默认 `max-height: 3em`，block 默认 `max-width: 100%`；1024px 级图不撑破版面（spec「投放方式与尺寸」）
- 块级语境下一条消息里的多张图各自成块、竖排（spec「投放方式与尺寸」）
- 流式生成过程中标记一写完整就出图（票 02 已有的核心行为是「半截标记保持原样」，实时出图的适配层收口放这里）；改任意设置后当前聊天立刻重渲染（spec「渲染」「投放方式与尺寸」；user story 48–55）

### 05 — 旧版本兼容路径与产出统一

- ST ≥ 1.19 走官方消息格式化钩子（`afterMarkdown`，DOMPurify 之前），与 1.15.0–1.18.x 的 DOM 路径行为一致（spec「渲染」、ADR-0002）
- 两条路径产出同一个类名与同一组 `data-*`：钩子路径写 `class="st-emote"`（由 ST 净化时加 `custom-` 前缀），DOM 路径写 `custom-st-emote`，CSS 只维护一份（spec「渲染」、ADR-0002）
- 重渲染、Show more、swipe、编辑消息后幂等，不重复插图、不残留旧图（spec「渲染」；user story 66）
- 关闭扩展后聊天里的图还原为原始标记文本（user story 66）
- 两条路径用同一套断言口径校验，测试夹具尽量用真实的 ST 渲染产物（spec「Testing Decisions」）

### 06 — 存储与生命周期

- 替换某张表情的图片，保留标签与描述（user story 4；spec「管理界面」）
- 删除单张、多选批量删除；删除整个包有二次确认且立刻删图（spec「存储」；user story 5、6、21）
- 外链：直接粘网络图片地址当表情，界面标注「外链」；外链失效按未命中处理（spec「存储」；user story 7、8）
- 上传格式限 `png` / `jpg` / `webp` / `gif`；单文件 ≤ 5MB 超限报错；上传时提示建议尺寸（高度 ≤ 512px）；动图保留动效（spec「存储」；user story 9、10、11）
- 跨设备（同一 ST 服务端）可见；图片没同步过来时该包标灰、仍可启用、可点进「重新指定图片」（spec「存储」；user story 31、32）
- 包导出为单个压缩包（图片 + 元数据：标签、描述、图片文件名、投放方式覆盖）；导入撞名拒绝并提示、导入后默认不启用（spec「存储」；user story 18、19、20、27）
- 一张图片只被一个表情使用，不允许共享引用（spec 领域模型 #2）
- 新建 / 导入的包默认不启用（新建部分 01 / 02 已满足；导入部分放这里）

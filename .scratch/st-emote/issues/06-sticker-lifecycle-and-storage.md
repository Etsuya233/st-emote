# 06 — 存储与生命周期：上传之后的一切

**What to build:** 表情上传之后的全部管理动作，以及图片本身的可靠性：替换、删除、批量删除、外链、格式与体积把关、跨设备后缺图的处理、以及把一整套表情打包搬走。

**Blocked by:** 01 — 闭环：一张表情能在消息里出现

**Status:** resolved

- [x] 能替换某张表情的图片，且保留它的标签与描述——`core/catalogue.js#replaceStickerImage` 只动 `image`，另有一条测试直接断言 `label` / `description` / `id` 在替换前后逐字不变；面板一侧由 `tests/panel.test.js` 驱动**真实的 `adapter/ui.js`**（jsdom 页面 + 假图片端点）走完「上传 → 替换」，断言旧文件被删、记录仍指向新文件。（文件选择器本身是 jsdom 里合成的，不是真的系统对话框。）
- [ ] 能删除单张，也能多选后批量删除；表情包删除有二次确认；删除后对应图片文件立刻消失——**判定与调用已逐条覆盖**（`tests/panel.test.js`）：单张删除、多选两张后批量删除、删包（同时从**三个作用域**摘掉包名并删除全部图片文件）、以及**拒绝后什么也不做**（`confirm` 返回 false 时记录数、文件删除调用数都不变）。删除的路径一律先过 `isOwnImagePath`（`core/image-rules.js`），非本扩展创建的文件永不进入删除集合。**未验证的两点**：① 确认框本身——测试走的是浏览器 `confirm` 兜底，ST 的 `callGenericPopup` 路径没被跑到；②「文件立刻消失」只验证了**发起了 `POST /api/images/delete`**，没有观察服务器上文件真的没了。
- [x] 能直接粘一个网络图片地址当表情，界面上标注「外链」；外链失效时按未命中处理——URL 规则在纯核心逐条测过（只收 http/https；空、拼错的、`data:`、`javascript:` 一律拒收，并归一成规范写法），面板测试断言外链表情带「外链」徽章且**没有本地文件可删**；「失效按未命中」由 `tests/dom-path.test.js` 断言：图 `error` 事件后它被移出聊天并写控制台。**未验证的是真实远端 404 的观感**，以及日志里 `image-missing` 与 `external-link-failed` 两种理由的区分（那条分支没有断言）。
- [ ] 上传只接受 `png` / `jpg` / `webp` / `gif`；单文件超过 5MB 被拒并说明原因；上传时给出建议尺寸（高度 ≤ 512px）提示；动图保持动效、不改帧——**格式与体积已完全覆盖**（`core/image-rules.js` + `tests/panel.test.js`）：四种格式与后缀折叠、大小写、`svg` / `bmp` / 无扩展名 / `png.txt` 一律拒收；**恰好 5MB 放行、5MB+1 拒绝**；面板层断言被拒时**不发请求**、且给出的理由可读（「larger than 5MB」/「not a png, jpg, webp or gif」）。「建议高度 ≤ 512px」的**判定谓词**（`exceedsSuggestedHeight`）已测，但**提示本身要靠 `new Image()` 量出真实高度才能弹**，jsdom 不会解码图片，所以**这条提示待目视**。「动图不改帧」是「我们根本不解码、不重编码、原样上传字节」这条性质，没有专门的测试。
- [ ] 同一台 ST 服务端的另一台设备上能看到同样的表情；图片文件没同步过来时该包标灰、仍可启用、可点进去重新指定图片——**判灰与恢复入口已覆盖**（`core/library.js` + 面板测试）：服务器报告目录里没有我们的文件时该包加 `st-emote-pack-missing`、出现「图片未同步」徽章、封面变成可点的「重新指定图片」入口、**三个作用域的勾选框照常可用**（缺图不禁用，是 spec 明确要求的）；文件都在时不标灰；`外链` 永不判为缺图；**取不到目录列表时不判灰**（宁可不说，也不把整个库标灰）。**未验证的是真的换一台设备**：这套判定依赖 `POST /api/images/list` 的真实返回，以及「另一台设备」的完整场景。
- [ ] 能把一个表情包导出成单个压缩包（内含图片与元数据：标签、描述、图片文件名、投放方式覆盖），也能导入别人给的包——**压缩包往返已覆盖**（`tests/archive.test.js`，用 JSZip 真读真写）：导出的 zip 里确实有 `st-emote.json` 和 `images/`，再读回来得到**同一个包清单**；**逐表情的投放方式覆盖跟着过来**（票 04 交接的那一条）；外链在包里只留地址、不塞字节；导出计划把「压缩包内路径 ↔ 本机文件 ↔ 表情」三者绑在一起而不是按位置配对（评审点名的那处脆弱）。**未验证的是导出下载与导入选文件的真实流程**：`downloadBlob` 的 `<a download>` 与文件对话框都没跑到。
- [x] 导入时包名已存在则拒绝并提示；导入后默认不启用——`planImport`（纯核心）按包名大小写不敏感地撞名即拒，面板测试端到端断言：包没被加进目录、**一个字节都没上传**、提示出现；导入成功后断言该包**不在任何作用域里**（`addImportedPack` 只读目录、不碰作用域），提示里也写明「not enabled anywhere yet」。
- [x] 一张图片只被一个表情使用，不存在共享引用——这条**没有单独的实现**，它是命名的推论：上传的文件名由该表情自己的 id 决定（`imageFileName`），两个表情因此不可能指向同一个文件；`planImport` 给每张导入的表情发**新 id**（有测试断言 id 互不相同，且每次上传各认各的表情）。`ownImageFilesOf` 另外做了去重与归属过滤。
- [x] 包列表用包内第一个表情的缩略图当封面，并保持按名字排序——`core/library.js` 的 `packCoverImage`（**字面的第一张**，与 spec 同措辞；第一张还没图时封面留空而不是借用后面那张）与 `sortPacks`（`Intl.Collator`，两个比较相等的包保持原有顺序），面板测试断言封面 src 与列表顺序。
- [x] 一个表情都没有的包允许存在，列表里显示为「空」——`packState` 读作 `empty`（面板徽章「空」）；**且空包在搜索时不会被筛掉**（无查询时所有包都保留，有一条测试专门钉住这条——否则「空」这一格永远显示不出来）。
- [x] 描述用于界面搜索（按标签 / 描述筛选表情）——`matchesQuery` 同时搜标签与描述，折叠方式与标签比较一致（大小写、多余空白不敏感）；面板测试覆盖：按描述搜、按另一张的描述搜、按标签搜、搜不到时的提示文案。
- [x] 改标签时给出与改包名一致的「旧标记会失效」提示——`core/library.js#renameBreaksTokens` 是与改包名**同一个谓词**（只是换成包名的比较函数），面板测试断言两种情况：真改名弹「Tokens using the old label no longer match.」，而只改大小写（归一化后等价、既有标记照样命中）**不弹**。

- 2026-09-28：已实现并提交。功能提交 `654d037`（feat: sticker lifecycle, image rules and pack import/export），评审修复提交 `d68e411`（fix: a replace must not delete the image it just stored, and an import must face the same image rules as a picked file）。`npm test` 279 项通过 / 0 失败 / 0 跳过。
- **纯核心新增四个模块**：`core/image-rules.js`（四种格式、5MB 上限、≤512px 建议谓词、什么算「外链」、以及归属判定 `isOwnImagePath`）、`core/catalogue.js`（替换 / 删单张或批量 / 删包 / 导入落地，各自报出该删哪些文件）、`core/manifest.js`（**包清单**格式 + `parseManifest` + `planImport`）、`core/library.js`（按名字排序、封面、包状态（`ok` / `空` / 图片未同步）、搜索、改名是否废标记的谓词）。规则全在纯核心里，`node --test` 直接跑。
- **适配层**：`adapter/archive.js` 用 ST 自带的 `/lib/jszip.min.js`（`await import()` 装全局）读写 zip 字节，**运行时不新增任何依赖**；`adapter/upload.js` 收成三个图片接口的调用（上传 / 删除 / 列出）外加「这条拒绝理由怎么跟用户说」；面板补齐替换图片、单张与批量删除（带确认）、「外链」徽章、缺图标灰 + 点封面重新指定图片、封面、「空」、搜索、改标签的失效提示。**缺图检测走一次 `POST /api/images/list` 拿整个目录**（比逐个探测便宜），取不到列表时**不判灰**。
- **拆分**：`adapter/ui.js`（1577 行）拆出 `adapter/sizing-panel.js`（投放方式与两套尺寸集的控件，234 行）与 `adapter/dialogs.js`（toast / 确认 / 输入框 / 剪贴板，82 行，每项都是「客户端 API 优先、浏览器 API 兜底」两条路）。`ui.js` 降到 1291 行，只剩表情包的列表与行。
- **评审抓到的两个 BLOCKER**：
  - ① **替换会把刚上传的图删掉**。上传文件名原本是 `st-emote-<id>.<ext>`，而客户的端点会把扩展名剥掉再按格式重贴，于是 png→png 的替换落在**同一个路径**上，紧接着的「删旧文件」删掉的就是新图，表情随即指向一个不存在的文件。**原来的测试没抓到，是因为它把上传桩写成了真实端点不可能返回的路径**。修法两条一起上：文件名加随机尾巴（新旧永不重名），外加 `replaceStickerImage` 在「旧路径 == 刚存的路径」时拒绝交出文件——单靠任一条都离 bug 回归只差一次重构。回归测试改成**让上传返回同一个路径**，并已验证：撤掉核心那层保护，该测试立刻失败。
  - ② **导入绕过了图片规则**，`planImport` 对认不出的格式**静默丢弃**（变成一张没图也没解释的表情），而且**完全不查体积**，40MB 的 gif 直接进。导入是「让任意 zip 的字节进图片目录」的通道，只管手动上传的规则不叫规则。修法：`planImport` 现在接收解压出的**真实字节数**（不信包清单里对方的自述），格式不在四种之内、超出 5MB、或文件读不出来，都**整包拒收**并给出具体理由；拒收时不返回任何半成品包，调用方没有东西要清理。这条同时把 ADR-0003 里刚写下的「不做部分导入」真正兑现。
  - 另外三个：③ 压缩包测试在**没有本机 SillyTavern checkout 时静默跳过**——一次什么都不证明的绿色 `npm test` 正好盖住本票唯一的新保证；改用 **devDependency `jszip`**，运行时照旧读客户自带的 `/lib/jszip.min.js`，**现在没有任何 skip 路径**（已实测：把 checkout 移走，测试照跑）。④ `清单` 在 `CONTEXT.md` 里已经是宏输出，导出包那份元数据改叫**包清单**（已补进词汇表，代码 / ADR / `common_dev.md` 统一）。⑤ 规则漏进适配层：文件对话框的 `accept` 列表与「larger than 5MB」这句话改为**从 `IMAGE_FORMATS` 与 `MAX_IMAGE_BYTES` 派生**。
- **两处与 spec 的对齐 / 偏差**：① 封面改为**字面的第一张表情**的图片（原先是「第一张有图的」）。spec 原文是「包内第一个表情的缩略图」，而借用后面一张会让封面说一件这个包并不是的事；第一张还没图时封面留空，旁边有状态徽章说明原因。② 删除确认按**一次确认**实现（`callGenericPopup`，兜底 `confirm`），不是连问两遍。
- 文档：`docs/adr/0003-sticker-storage.md` 追加「归属靠文件名前缀判定」与「导出包的格式」两节（写明包清单为什么不记录本机存储路径、为什么导入必须过图片规则）；`CONTEXT.md` 补上「包清单 (Export manifest)」词条。
- 一个值得记的测试教训：评审修 B2 时，测试里「等固定几个事件循环轮次」对 6MB 的 zip 不够，**没跑完的工作把提示串到了下一个测试的 `toastr` 里**。改成「等到条件成立」而不是「等够久」——猜错了不只是失败，还会污染邻居。

## 待人工验收（下次统一验证）

- [ ] **建议高度 ≤ 512px 的提示**：判定谓词已测，但提示要靠 `new Image()` 量出真实高度才弹（jsdom 不解码图片）。上传一张高度明显超过 512px 的图，确认提示出现、文案说明这仍是建议而非拒绝，且图照常可用；再确认一张正好 512px 的不提示。
- [ ] **真正的跨设备场景**：在一台机器上传并启用若干包，在连同一台 ST 服务端的另一台设备上打开面板——表情与元数据都在，但图片文件没同步过来的那个包应当标灰、显示「图片未同步」、**仍然可以勾进作用域**，点封面能进入「重新指定图片」，换完立刻恢复。**这条是本票最需要在真机上走一遍的**。
- [ ] **删除的确认框**：在真 ST 里删单张、批量删、删整包，确认弹的是客户自己的对话框（不是浏览器的 `confirm`），文案说清了会删几张表情和图片文件；点取消则什么也不动。再确认删完之后 `user/images/st-emote/` 里对应的文件**真的没了**。
- [ ] **导出与导入的真实流程**：导出一个包，确认浏览器真的下载到一个 zip、解压后 `st-emote.json` 与 `images/` 都在（外链只留地址）；再把同一个 zip 导入回来，确认提示里写明「未启用」、该包不在任何作用域里、勾上后聊天里就能出图。顺带确认导入一个撞名的包时提示清楚且什么都没发生。
- [ ] **依赖 1.19 的遗留项（承接票 05）**：本票把「图加载失败就移出并记日志」的守卫从 DOM 路径**挪到了选路径的那一层**，好让钩子路径上死链与缺图也按未命中处理（`external-link-failed` / `image-missing` 两种理由）。这条在 ≥1.19 的钩子路径上**完全没跑过**，需在 1.19+ 上确认死链会被移走而不是留一个裂图图标。票 05 清单里其余依赖 1.19 的项（钩子端到端、ST 净化是否保留 `style` 与 `data-*`、跨版本观感对比）原样仍在。

- **只在真服务器上才能验的**：删除后磁盘上的文件是否确实消失、图片目录列表在真实账号下的返回形状、以及跨设备同步的完整链路——这些都没有自动化替代，仍在上面的待办里。

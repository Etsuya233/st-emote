# 05 — 旧版本兼容路径与产出统一

**What to build:** 用旧版 ST 的用户（1.15.0–1.18.x，没有官方消息格式化钩子）能看到与新版完全一样的表情：同样的位置、同样的尺寸、同样的类名。关闭扩展或改动设置后，聊天里的图能干净地还原，反复重渲染不会叠加。

**Blocked by:** 04 — 投放方式与尺寸

**Status:** resolved

- [ ] 在 ST 1.15.0–1.18.x 上，01–04 的全部渲染行为（标记形态、命中规则、未命中、投放方式、尺寸、多张竖排）与 1.19.0 以上的表现一致——**01–04 的每一项行为都已逐条拿两条路径对拍**（`tests/render-paths.test.js`：驱动真实钩子适配层与真实 DOM 适配层，共用一份期望表，覆盖两种标记形态、裸标签、重复标记、代码块跳过、六种未命中、用户 / 系统 / 旁白的处理范围、三种投放方式、逐表情覆盖、两套尺寸集、多张块级图、群聊按作者取作用域；思考链只测了钩子路径的 `isReasoning`，DOM 路径上它渲染在 `.mes_text` 之外、天然够不着）；**但对拍的两侧是"适配层 + jsdom / 假 messageFormatter"，不是真实客户端**，≥1.19 的端到端无法在本机验证（本地 ST 是 1.18.0，没有 `messageFormatter`），竖排观感仍来自 CSS `display: block`
- [ ] 两条路径产出的元素带同一个类名与同一组 `data-*` 标识，样式只需维护一份——契约本身已钉住：`STICKER_CLASS` 由 `SANITIZER_CLASS_PREFIX + STICKER_HOOK_CLASS` **派生**（不是各写各的，改基类名时两边一起动），钩子路径发不带前缀的 `st-emote`、DOM 路径发 `custom-st-emote`，对拍断言两边的类名列表与 `data-*` 名称集合完全一致，`style.css` 始终只有一份；**未验证的是客户那一侧**：ST 净化是否真的给两个类名都补上 `custom-`、是否保留 `style` 与 `data-st-emote-token`（测试里模拟了这一步，标注为 model）
- [x] 重渲染、加载更早的消息（Show more）、swipe 切换、编辑消息之后，不出现重复插图或残留旧图——对真实 DOM 适配层逐项验证（`tests/dom-path.test.js`）：同一消息首渲后再渲两次仍只有一张图；块后图第二轮不会被再次搬动；Show more 追加更早消息后总数正确且原有消息不变；swipe / 编辑后恰好一张图且是新标记那张；改设置后按源文本重渲并重新应用投放方式。钩子路径没有可泄漏的 DOM 状态（每条消息都由客户重新跑一遍钩子），另测了重复调用 `installRendering` 不会注册第二个钩子
- [ ] 关闭扩展后，聊天里的图恢复为原始标记文本——**还原本身已验证**：图上的 `data-st-emote-token` 记着标记原文（不依赖表情包还启用着），先用客户源文本重排、再把剩下的图就地换回标记，因此块后图能回到模型写它的段落里，流式预览这类没有源文本的也保底还原；重复还原是幂等的，消息里与扩展无关的 `<img>` 不受影响；关闭后**再触发任何渲染事件也不会把图插回来**（`domPathInstalled && isRenderingEnabled()` 门在遍历里面，不在订阅外面）；钩子路径关闭后变成直通；**未验证的是面板那一圈**：ST 真的调用我们导出的 `onDisable`、且不刷新页面
- [x] 两条路径用同一套断言口径校验（只断言最终 DOM 的结构、类名与尺寸样式，不断言实现方式）——`tests/contract/render-contract.js` 是唯一的一份期望与唯一的断言入口，两条路径各自跑完后都被送进同一个 `assertRendersAs`；断言只读最终 DOM 的元素顺序、类名列表、`data-*` 与内联尺寸样式，其中模拟的客户行为只有"净化补 `custom-` 前缀"一处且当场标注为 model。**这套契约抓到了票 04 的一个真 bug**（见下），说明它是活的守门人而不是摆设

## Comments

- 2026-09-28：已实现并提交。功能提交 `2cbe6e5`（feat: official message hook, unified output and a clean way out），评审修复提交 `b16e918`（fix: gate the DOM path on disable, and make the parity test real）。`npm test` 190 项通过 / 0 失败。
- **两条路径**：`adapter/hook.js` 是 ST ≥ 1.19.0 的官方钩子路径（`messageFormatter.addHook`，阶段 `afterMarkdown`、早于净化），`adapter/rendering.js` 保留 1.15.0–1.18.x 的 DOM 后处理。**只装一条**，由特性探测决定（`supportsMessageFormatter` 只看 `addHook`，不做版本号判断）；钩子装不上（签名不同、抛错）时回落到 DOM 路径，因为后者在 1.15.0 起的每个版本都能用。
- **产出统一**：`core/render.js` 里 `STICKER_CLASS` 改为**派生**——`SANITIZER_CLASS_PREFIX + STICKER_HOOK_CLASS`；钩子路径发不带前缀的 `st-emote`、由 ST 净化补 `custom-`，DOM 路径发最终的 `custom-st-emote`，两边因此不可能漂移。行为标识一律走 `data-*`（ADR-0002），由 `stickerHtml` 一处发出。
- **两条路径共用一层**：`adapter/render-common.js` 收口设置、拼生效集、判处理范围、写控制台；`core/processing-scope.js` 收口处理范围规则本身（原先两条路径各写一份）。差异只允许存在于"结果怎么进 DOM"这一步。
- **还原**：`manifest.json` 声明 `hooks.enable` / `hooks.disable`，`index.js` 导出 `onEnable` / `onDisable`。扩展面板的关闭动作不刷新页面，所以关掉时要自己做还原：图上记着 `data-st-emote-token`（标记原文），先用客户源文本重排、再把剩下的图就地换回标记。钩子在关闭后**仍然注册着**（撤不掉），所以靠一个开关让它变成直通。
- **测试**：新增 dev 依赖 `jsdom`，DOM 路径与入口点是拿**真 DOM** 端到端跑的（`tests/contract/st-dom.js` 只伪造客户接口面：`getContext`、事件总线、`updateMessageBlock`；DOM 本身是真的）。`tests/entry.test.js` 直接 import 真实入口模块——这是适配层各测试文件覆盖不到的（那一版的 `adapter/macro.js` 就因为改了 `LOG_PREFIX` 的位置而整个入口挂掉，而适配层测试当时全绿）。既有测试不再手抄 `<img>` 标记，改为从共享契约生成。
- **评审抓到的五个问题**（Standards 与 Spec 两轴）：① DOM 路径完全无视关闭标志——事件订阅活过 `onDisable`，下一次渲染事件就把图插回一个"已关闭"的扩展里；门必须放在遍历里面而不是订阅外面。② `rerenderChat` 读的是启动时捕获的 `context.chat`，换聊天后会重排上一个聊天（这条是本票自己引入的回归）。③ `tests/contract/render-contract.js` 里埋了 3 个字面 NUL 字节做哨兵，git 把整个文件当二进制存，没有 diff 也没有 blame；哨兵其实完全不需要（`<img>` 对 `textContent` 毫无贡献）。④ 钩子路径把旁白硬编码成 `isSystem: false`，而"旁白就是系统消息"是**没有证据的假设**——查了 ST 源码，`system-messages.js:40,104` 只给真系统消息设 `is_system: true`，`script.js:5750,7267,8125` 把 `is_system` 与 `extra.type === 'narrator'` 当作**两个并列情况**判断；改成用 `messageId` 回查聊天，与 DOM 路径读元素 `type` 属性（客户从同一个 `extra.type` 拷过去的）对应。⑤ 原来的两路径对拍是拿 `core/render.js` 跟自己比（只差一个 `className` 选项），两个真实适配层根本没被比较过——纯核心是共用的，跟自己比证明不了任何事。
- **⑤ 直接赚回本：新的对拍测试当场抓到票 04 的一个真 bug。** DOM 路径挑落点时只看 `blockBoundaryMode`，而它答的是"块内哪个位置"、**根本不读投放方式**，于是写在一段里的「消息末尾」图被判成 `after` → 落到了 `</p>` 之后，也就是**「消息末尾」在旧版路径上被静默当成「块后」**（图照常出现，位置不对，很难归因）。修法：投放方式决定"去哪个地方"，块边界只决定「块后」里的具体落点（表格单元留在单元格内那条有意偏差不变）。已由 `dom-path.test.js` 的两条落点测试钉住。**票 04 的读者请注意：这条在 04 的纯核心测试里是抓不到的**，因为核心自己的 `relocatePlacedImages` 一直是对的，错的只有 DOM 适配层那一侧。

## 已知取舍与偏差

- **还原分两段**：先用客户的源文本重排（有源文本的，块后图能回到模型写它的段落里），再把剩下的图就地换回标记（流式预览这类没有源文本的保底）。第二段只能把标记放回**图现在所在的位置**，因为重定位之后 DOM 里已经没有任何东西记着它原来写在哪。
- **钩子关不掉只能变直通**：`messageFormatter` 没有已知的注销接口（不确定就不去调它），所以关闭时靠一个开关让钩子原样返回消息。
- **DOM 路径整体门控在 `domPathInstalled && isRenderingEnabled()`**：前者让不区分路径的调用方（改设置、重新启用）不会在钩子路径的客户端上白跑一趟遍历；后者保证关闭扩展后事件不会再把图插回来。两者都在遍历里面，因为事件订阅活过关闭动作。
- **`applySanitizerClassPrefix` 是模拟，不是客户**：契约里只模拟"净化补 `custom-` 前缀"这一处，因为那正是让两个类名相等的那一步；再多模拟就等于开始测自己的模型而非测代码。
- **测试需要 `npm install`**（dev 依赖 `jsdom`），但扩展本身没有构建步骤、不依赖它；`core/` 仍然不依赖 ST 也不依赖 DOM。

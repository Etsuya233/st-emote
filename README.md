# st-emote

SillyTavern 扩展：模型在回复里用标记指名表情，扩展把标记渲染成表情图片。

模型写 `[[sticker:daily:happy]]`，聊天里就出现一张 happy 表情的图片。你自己准备图片、自己给每张图起一个短标签、自己决定哪些表情在哪些场合可用；扩展只负责把标记换成图。

- **界面中英双语**，跟随 SillyTavern 的语言设置。
- **不碰你的提示词**。可用表情清单由你自己在预设里用宏 `{{st-emote}}` 取，扩展不会往提示词里注入任何东西（见 [这条边界](#这条边界扩展不碰提示词)）。
- **最低支持 SillyTavern 1.15.0**（见 [兼容性](#兼容性)）。

---

## 安装

仓库没有构建步骤：SillyTavern 直接把目录里的 `manifest.json`、`index.js` 与 `style.css` 当静态站点加载。所以「安装」就是把这个目录放进 SillyTavern 的第三方扩展目录。

### 方式一：链接一个本地 checkout（开发用）

把仓库链到 `public/scripts/extensions/third-party/st-emote`。Windows 上用 Junction，不需要管理员权限：

```powershell
powershell -NoProfile -Command "New-Item -ItemType Junction -Path '<SillyTavern>/public/scripts/extensions/third-party/st-emote' -Target '<本仓库路径>'"
```

Linux / macOS 用软链：

```bash
ln -s /path/to/st-emote /path/to/SillyTavern/public/scripts/extensions/third-party/st-emote
```

链上之后改代码只要刷新浏览器，不必重启 SillyTavern；`manifest.json` 改了才需要重启。

### 方式二：直接放进扩展目录（普通安装）

```bash
git clone https://github.com/Etsuya233/st-emote.git \
  /path/to/SillyTavern/public/scripts/extensions/third-party/st-emote
```

装完在 SillyTavern 的「扩展」面板里启用 **st-emote**。装上之后它默认是启用的，而且在没有任何已启用表情包之前它什么都不会做。

## 三步用起来

1. **建一个表情包**，往里上传图片（`png` / `jpg` / `webp` / `gif`，单张 ≤ 5MB，不压缩、不重编码，gif 的动效原样保留），给每张图填一个**标签**和一个描述。标签就是模型会用的名字。
2. **在某个作用域里启用它**。见下面[三层作用域](#三层作用域)。
3. **在预设里写一行宏** `{{st-emote}}`，告诉模型有哪些表情可用，并按你要的方式指示它写标记。

第 3 步是唯一需要你自己动手的一步，也是这个扩展的边界所在。

---

## 三层作用域

配置分三层，每层各自持有一组「已启用的表情包」：

| 作用域 | 存在哪 | 什么时候生效 |
| --- | --- | --- |
| **全局** | 扩展设置 | 所有角色、所有聊天 |
| **角色** | 角色卡的扩展字段 | 这个角色参与的聊天（群聊里按每条消息的作者分别解析） |
| **聊天** | 聊天元数据 | 只是这个聊天 |

**生效集 = 三层启用表情包的并集**，按包名去重。**并集是纯的：只能加，不能减。** 没有排除、没有覆盖、没有优先级。

于是「某个表情包为什么没生效」永远只有一个答案：勾上它。相应地，**在一个作用域里停用另一个作用域启用的包不会让它消失**——停用的意思只是「这一层不再参与」。

几条跟着这条规则走的行为：

- 同一张表情图可以同时被三层启用，互不影响。
- 新建、导入的表情包**默认一个作用域都不启用**，不会悄悄开始生效。
- 包名全应用唯一，可以直接用在标记里当限定名。角色卡引用了本地没有的包时，面板会列出「缺失的表情包」，可以一键建出空壳再补图。

群里每个人的角色层配置按**该条消息的作者**生效，所以同一条群聊里两个角色可以带不同的表情包。

## 宏：把清单写进你自己的预设

注册在扩展里的宏只有一个，展开成**清单**——生效集里每个有标签的表情一行，两档都带表情包名。

| 写法 | 展开成 |
| --- | --- |
| `{{st-emote}}` | 每行一个 `表情包名:标签 (描述)`（等同 `::full`） |
| `{{st-emote::full}}` | 同上；**描述为空时整段就是 `表情包名:标签`**，没有括号 |
| `{{st-emote::simple}}` | 每行一个 `表情包名:标签`，不带描述 |
| 生效集为空时 | 一个「无」字 / the word for "none" |
| [总开关](#总开关)关掉时 | 空串（不是「无」——表情包还启用着，只是不会被渲染） |

描述就是你在面板里写的那句话，原样进入清单，**不改写成祈使句**——扩展不替你写任何「你应该这样用」之类的指令文本。

在**你自己的预设**（或世界书、角色卡字段）里写下它，比如：

```
你可以用这些表情：{{st-emote::simple}}
每条回复最多用 3 个，用 [[sticker:表情包名:标签]] 的形式指名。
```

清单每次构建提示词时实时算，所以你启用新包后**下一轮就生效**，不需要任何刷新动作。清单语言跟随 SillyTavern 的界面语言。

> `::simple` 省 token——一个几十张表情的包，带上描述的清单会明显更长。**两档都不解决裸标签的歧义**：同一层里两个包都定义了 `happy` 时，模型写 `[[sticker:happy]]` 仍然算**未命中**，要写 `[[sticker:表情包名:happy]]`。用 `/st-emote conflicts` 查一下就知道有没有。

### 这条边界：扩展不碰提示词

**扩展从不修改、注入或整理你的提示词。** 它不使用 `setExtensionPrompt` 之类的注入机制，也不会往你的预设里塞任何文本。

这意味着两件事：

- 清单里只有数据，没有一句「你应该这样用」之类的指令文本。想怎么引导模型写标记，完全是你的预设说了算。
- 代价是**宏要你自己写一次**。忘了写，模型就不知道有哪些表情可用——这是可见的、可接受的失败方式，而不是一个悄悄改坏你提示词的 bug。

面板里另有一段可复制的正则 JSON，用来**只把标记从上下文里清掉**（聊天里该显示什么还是显示什么，包括[未命中的标记文本](#未命中)）。复制后在正则扩展里以 "Import To: Global" 导入即可。扩展不会自动替你注入它。

## 标记怎么写

| 形态 | 写法 |
| --- | --- |
| 标记式（默认） | `[[sticker:表情包名:标签]]` |
| HTML Tag 式 | `<sticker>表情包名:标签</sticker>`（标签名可在面板里改，默认 `sticker`） |

**两种形态各自能单独关掉**（面板上有两个勾选框）。关掉的那一种不再是语法：文本原样留在聊天里，**不算未命中**。关掉 HTML 标签式时标签名输入框会置灰——设置还在，只是不生效；两个都关是合法状态，面板会提示一句，此时任何标记都不会渲染。

关掉的形态**也不再被面板那份「只从上下文清掉标记」的正则剥掉**，JSON 会在形态变化时重新生成。否则你会遇到最难查的一种现象：写 `<sticker>…</sticker>`，聊天里什么都没发生，提示词里却也没了。

- 按**第一个 `:`** 切分：左边是表情包名，右边是标签。
- **生效集只有一个表情包时**可以省略包名：`[[sticker:标签]]`。
- **生效集有多个表情包时**，裸标签一律算未命中，不猜。
- 同一个标记出现几次就插几张图。
- 代码块与行内代码里的标记不渲染。
- 标签比较忽略大小写和多余空白（`Happy`、`happy `、`HAPPY` 都能命中同一张），但**存储保留你的原文**。
- 标签最多 32 码点，不能含 `[` `]` `<` `>`，不能换行；表情包名同样，且不能含 `:`。
- **改了包名或标签，之前写好的标记就不再匹配。** 操作时面板会提醒你。已经渲染出来的旧消息不受影响，但下次重渲染时算未命中。

### 未命中

`Miss['reason']` 有六种，都算**未命中**：

| 理由 | 意思 |
| --- | --- |
| `pack-not-found` | 没有叫这个名字的表情包 |
| `pack-not-enabled` | 有这个表情包，但当前作用域（全局 / 角色 / 聊天）没有启用它 |
| `label-not-found` | 那个表情包里没有这个标签 |
| `ambiguous-bare-label` | 启用了一个以上的表情包，裸标签因此有歧义 |
| `image-missing` | 标签命中了，但那张图不在这台服务器上 |
| `external-link-failed` | 外链的地址打不开 |

最后两种要等图真的画不出来才知道，所以由一条 `error` 事件兜住，两条渲染路径上都一样。

**未命中的标记留在聊天里**，形态与你写的一致——写的是 `[[sticker:…]]`，留下来的就是 `[[sticker:…]]`；写的是 `<sticker>…</sticker>`，留下来的就是 `<sticker>…</sticker>`。两者都显示成**字面文本**，而不是一个会被浏览器当成元素、于是只剩裸名字的标签。同时在浏览器控制台里记一行。

这样排错时能直接看见模型写错了什么，比一个空缺有用得多。代价是聊天里会留下一些没画出来的标记文本；不想让它们进入上下文的话，用下面[那条只清上下文的正则](#这条边界扩展不碰提示词)（显示端照常不动）。

`image-missing` 与 `external-link-failed` 两种同样退回标记文本，而不是留一个裂图图标。

> 代码块与行内代码里的标记一律不处理，**算不算未命中都不算**——它们本来就是给人看的文本。

（启用了一个包但没有图片的包是允许的，界面标灰、点封面是「重新指定图片」入口——这不算未命中，只是图没跟过来。）

## 投放方式与尺寸

**投放方式**决定表情图出现在哪里：

- **原地**：标记写在哪里，图就出现在那里。
- **块后**：当前段与下一段之间。
- **消息末尾**：整条消息的末尾。

全局设一个默认值，个别表情可以单独覆盖。改一张表情的投放方式等于同时切到另一套尺寸集——**间隙也跟着换**，因为两个字段的默认值方向本来就不同。

**尺寸集**分两套：`inline` 管原地，`block` 管块后与消息末尾。每套是最小/最大宽高 + 填充方式（`cover` / `contain` / `fill`）+ **一对间隙字段**（左右 / 上下），值以 `em` / `px` / `%` 手写，**原样交给 CSS**。

- `inline` 套默认 `max-height: 3em`、左右间隙 `0.15em`；`block` 套默认 `max-width: 100%`、上下间隙 `0.25em`；其余留空。
- `1em` = 当前聊天的文字高度。
- `0` 是合法值，也正是「我要贴紧」的写法。
- **只有宽度方向的 `%` 有保证**：高度的百分比取决于父元素自身有没有高度，CSS 不承诺。
- 填了非法值（`3rem`、`12`）**不会被拦下**，只是当成未设置，并在输入框旁边提示；同时控制台记一行。间隙字段的行为与尺寸字段完全一致。
- **间隙只有一个来源**：字段没配时走字段默认值，`style.css` 里没有第二条 `margin` 规则与它互相打补丁。

块级语境下同一段里的多张图竖排，不并排。未命中的标记**从显示中消失**，所以间隙只落在真正画出来的图上。

## 总开关

面板顶部有一个**总开关**（`/st-emote on` / `off` 是同一个开关的另一个入口）。关掉之后：

- 聊天里不再出现任何表情，**已经把图渲染出来的消息立刻退回标记**——不需要刷新页面。
- `{{st-emote}}` 宏**不再展开清单，返回空串**。这是一个有意收紧的边界：[上面那条「不碰提示词」](#这条边界扩展不碰提示词) 的原话是「扩展从不修改你的提示词」，理由是宏是你自己写进预设的；但反过来想——渲染已经关了还递一份清单给模型，是在诱使它认真写一堆永远不会被渲染的标记。所以关掉宏，面板上也把这条连带效果写明了。
- **ST 自己的扩展开关与它互不干扰。** 两者动的是同一个内部标志（`adapter/restore.js` 的 `renderingEnabled`），所以「在 ST 面板里关掉再打开」之后，扩展回到**它自己的开关所决定的状态**。
- 开关状态存在设置里，重启后保持。

**调试区的「试渲染」不受总开关约束**：它粘的是文本、不是聊天，而且「关掉了」往往正是你想调试的状态。这是有意的不一致，理由写在 `core/preview.js` 的模块注释里。

## 调试与操作

### 调试区（「试渲染」）

面板里有一个框：粘一段消息进去，点「试渲染」，立刻看到它按当前设置渲染成什么样，**聊天记录一个字都不动**——不写消息、不重渲染、不保存设置。未命中的标记在这里**和聊天里一样留在原位**，框下那一行另外说明哪些没画出来，细节在控制台。

它走的是和聊天完全相同的那段渲染逻辑，所以**投放方式、尺寸、间隙、代码块跳过、标记形态开关都是真的**：块后图真的会落到段后而不是原地，写在代码块里的标记真的不会被渲染，关掉的形态真的不出现。粘进去的文本会先经过 ST 自带的 markdown 转换（和聊天消息同一步），所以 ``` 围栏和表格的行为一致；如果这个客户端没有提供转换器，就按纯文本处理，面板的提示里会写明这一点。

旁边的「重新渲染当前聊天」按钮手动刷新当前聊天，适合改完设置想立刻看一眼。它在两条渲染路径上都有效：在 1.19+ 上是把每条消息交还给客户端重跑一遍它自己的格式化流程（钩子就是其中一个环节），在 1.15.0–1.18.x 上额外再跑一次 DOM 处理。

### 斜杠命令

| 命令 | 作用 |
| --- | --- |
| `/st-emote enable pack=daily scope=chat` | 在某个作用域启用一个表情包 |
| `/st-emote disable pack=daily scope=global` | 在某个作用域停用 |
| `/st-emote off` | 关闭扩展本身（总开关） |
| `/st-emote on` | 重新打开扩展本身 |
| `/st-emote reload` | 重新渲染当前聊天 |
| `/st-emote conflicts` | 列出生效集里的标签冲突 |

`scope` 可取 `global`（默认）/ `character` / `chat`。命令只回报一句话，不抛异常；`/st-emote` 后面什么都不写会告诉你有哪些动作可用。

`on` / `off` 与面板上的总开关走**同一个入口**，不接受 `pack` 或 `scope`。

`reload` 不重读也不保存设置（它做不到，也不想覆盖你手工改过的设置文件）——它做的事就是上面那句「重新渲染」。

### 「查冲突」查的是什么

一个**冲突**是：**生效集里有两个或更多已启用表情包定义了同一个（归一化后）标签**。

它让裸标签 `[[sticker:标签]]` 在这一刻成为歧义（按未命中处理）。清单不受影响：两档清单的每行都带表情包名，所以同一个标签在两个包里得到的是 `daily:happy` 和 `roleplay:happy` 两行不同的内容。命令会列出这些标签，并指出各自由哪些包定义、包里写的是哪个拼法。

只看**已启用**的包：关掉一个包，对应的冲突立刻消失。空集报「没有冲突」，不是一张空表。

### 日志

未命中、冲突、被忽略的尺寸值**只写浏览器控制台**，统一带 `[st-emote]` 前缀：

```
[st-emote] sticker not rendered (label-not-found): daily:hoppy
[st-emote] label conflict: "happy" is defined by daily, roleplay ("Happy")
[st-emote] size value ignored, treated as unset: maxHeight = "3rem"
```

界面里**没有日志面板**。这三行的字面写法都有测试钉住（`tests/dom-path.test.js`、`tests/commands.test.js`），所以文档里的例子不会和实际输出漂掉。

## 表情包导出与导入

**导出**写出一个 zip：图片文件 + 一份 `st-emote.json`（**包清单**，描述包名、每个表情的标签与描述、逐表情的投放方式覆盖，以及图片来源是包内文件还是外链地址）。外链只留地址，所以分享出去的链接不会冻结成今天这张图。

**导入**把这样的 zip 读回来：图片走和手动上传完全一样的格式与体积规则，一条不过就整包拒收。

- 包名已存在 → **拒绝并提示**，不自动改名、不覆盖。
- 导入完**在任何作用域里都不启用**，直到你自己勾上。
- 缺文件的包 → 界面标灰，仍可启用，点封面是「重新指定图片」。

---

## 存储

- 图片写进 SillyTavern 自己的用户数据目录（`user/images/st-emote/`），经由 ST 自带的上传接口写入。元数据在扩展设置里。
- 同一台 ST 服务端的另一台设备上能看到同一批表情（图片没跟过去时界面标灰并给补图入口）。
- 角色卡的扩展字段里只存「启用了哪些包」，不存图片——导出角色卡不会带走图片。
- 删除单张表情或整个包会立刻删掉对应文件（删整包有二次确认）。**归属判定只认目录 + `st-emote-` 前缀**，别的目录里的文件一律不碰。
- 允许**外链**（图片不落盘，只存地址），界面标注出来。
- 不接受 SVG，不自动压缩任何图片。

## 兼容性

**最低支持 SillyTavern 1.15.0**，写在 `manifest.json` 的 `minimum_client_version` 里；低于这个版本的 ST 会拒绝加载本扩展，扩展自己不判断版本。

渲染走两条路径，**只装一条**（按特性探测）：

| 客户端 | 路径 | 怎么做的 |
| --- | --- | --- |
| ≥ 1.19.0 | 官方消息格式化钩子（`afterMarkdown`，净化之前） | 发 `class="st-emote"`，ST 净化时补上 `custom-` |
| 1.15.0 – 1.18.x | DOM 后处理 | 直接发最终的 `custom-st-emote` |

两条路径**产出完全相同的类名、相同的 `data-*` 属性、相同的尺寸样式，共用同一份 CSS**。命中规则、投放方式、尺寸求值都在同一个纯核心里，只差「结果怎么进 DOM」这一步。行为标识一律用 `data-*`，不用类名——所以你在设置里看到的每一个开关在两个版本上行为一致。

**处理范围**（一条消息是否参与渲染）与作用域无关：AI 输出处理，用户消息由开关决定（默认不处理），系统消息、旁白与思考链不处理。

## 开发者

架构只有一条缝：**纯核心 ↔ ST 适配层**。

- `core/` — 纯逻辑，不依赖 SillyTavern、不依赖 DOM：标记解析、生效集与三层作用域、清单生成、渲染拼装、投放方式与尺寸求值、冲突检测、图片规则、表情库生命周期、表情包包清单格式、界面文案目录。
- `adapter/` — 薄适配层：读写设置、上传、设置面板、两条渲染路径、斜杠命令、调试区。
- `tests/` — 纯核心测试 + 共享断言契约 + 两条渲染路径的对照 + 面板与压缩包的集成测试。

```bash
npm install   # 只为测试装 jsdom / jszip；扩展本身不依赖它们，也没有构建步骤
npm test
```

运行期**不新增任何依赖**：zip 读写用 ST 自带的 `/lib/jszip.min.js`，i18n 用本扩展自己的纯目录而不是 ST 的 `translate`（这样面板和宏共用同一份文案）。

# 双渲染路径，且两条路径产出同一个类名

ST 1.19.0 才提供官方消息格式化钩子（`afterMarkdown`，DOMPurify 之前），而本扩展要支持 1.15.0 起的版本，所以保留 DOM 后处理作为旧版路径。代价是两条路径产出的 DOM 必须手工保持一致：类名统一为 `custom-st-emote`（钩子路径写 `class="st-emote"`，由 ST 净化消息内容时统一加上 `custom-` 前缀；DOM 路径由我们自己添加），行为标识一律用 `data-*` 属性，CSS 只写一份。

**Consequences**：不写这条约定，后来者会把那个"多余的 `custom-` 前缀"当成 bug 修掉，从而静默破坏旧版本；新增任何视觉属性时都要同时照顾两条路径。DOM 路径还必须幂等（重渲染、Show more、swipe、编辑消息都不能重复插入）。

## 追加：块级修饰类（票 04）

`custom-st-emote` 是**每一张**表情图都要带的基类，投放方式为块后 / 消息末尾的图在此之上**追加**修饰类 `custom-st-emote-block`（钩子路径写 `st-emote st-emote-block`，净化后同样得到 `custom-` 前缀的两个类）。也就是说基类永远在场，修饰类只做加法。

**为什么**：`img.custom-st-emote` 是 DOM 路径挑选表情图的唯一入口（投放方式重定位、加载失败清理都靠它）。如果块级图只带修饰类而丢掉基类，选择器就再也匹配不到它们，块级投放方式会在旧版路径上静默失效，而且失效的表现是"图还在、就是不动"，很难归因。投放方式本身是**行为**，由 `data-st-emote-placement` 表达，类名只表达**呈现**——这与本 ADR 一贯的"行为标识一律用 `data-*`"是同一条规矩。

**Consequences**：不要把 `-block` 当成基类的替代写法；也不要把 `max-height` 这类只对某一套尺寸集成立的属性放回基类 CSS 里（块级图也会带基类），否则它会顺着基类漏到块级图上。尺寸一律由图片上的内联 `style` 承担，基类只留两种投放方式都成立的兜底值。

## 追加：路径选择与共用的产出契约（票 05）

两条路径**只装一条**，由特性探测决定：`messageFormatter.addHook` 存在就装钩子路径，否则装 DOM 路径。不做版本号判断，也不同时装两条——同时装会让每个标记渲染两次，并让两套投放逻辑互相抢同一张图的位置。

装好之后，两条路径的每一步都由同一份代码给出：命中与未命中、两种标记形态、投放方式、尺寸求值都在 `core/render.js` 里；`adapter/render-common.js` 是两条路径共用的那一层（读设置、拼生效集、判处理范围、写控制台）。**路径之间只允许存在的差异，是"结果怎么进 DOM"**。因此新增任何行为只有一处可改，两条路径自动一致。

类名由 `STICKER_HOOK_CLASS` 派生而不是各写各的：`STICKER_CLASS = SANITIZER_CLASS_PREFIX + STICKER_HOOK_CLASS`。DOM 路径写派生后的名字，钩子路径写派生前的那个，两边因此不可能漂移。`data-*` 集合同理，由 `stickerHtml` 一处发出。

**为什么用同一套断言**：`tests/contract/render-contract.js` 把"一张表情在最终 DOM 里长什么样"写成一份期望，两条路径各自跑完后都被送进同一个 `assertRendersAs`。断言只碰最终 DOM 的结构、类名、`data-*` 与尺寸样式，不碰任何实现细节——否则"两条路径一致"这句话就没人守着了。契约里只模拟了客户的一处行为（净化时加 `custom-` 前缀），因为那正是让两个类名相等的那一步；再多模拟就等于开始测自己的想象。

**断言必须驱动真实的适配层，不能拿纯核心跟自己比**。`core/render.js` 两条路径共用，所以拿它跟它自己比只能证明函数自洽，证明不了两个适配层一致。`tests/render-paths.test.js` 因此驱动钩子适配层（一个录制的 `messageFormatter`）与 DOM 适配层（真的 jsdom 聊天），再把两边交给同一份期望。**这条已经赚回本了**：改成这样之后立刻暴露出一个纯核心测试永远抓不到的真 bug——DOM 路径只用 `blockBoundaryMode` 决定落点，而它答的是"块内哪个位置"、根本不看投放方式，于是「消息末尾」被当成了「块后」（票 04 遗留）。投放方式决定"去哪个地方"，块边界只决定「块后」里的具体落点。

**处理范围在两条路径上的读法不同，但规则只有一份**（`core/processing-scope.js`）。特别地「旁白」：钩子的 frozen context 没有旁白标志，而 `isSystem` 也不覆盖它——客户在好几处把 `is_system` 与 `extra.type === 'narrator'` 当作两个并列情况判断，所以钩子路径必须用 `messageId` 回查聊天，DOM 路径则读元素上的 `type` 属性（客户端从同一个 `extra.type` 拷过去的）。少这一步，就恰好是"旁白只在 ≥1.19 被渲染"。

**关闭扩展要把聊天还原**。扩展面板的关闭动作不刷新页面，所以 `manifest.json` 声明了 `disable` 钩子，`index.js` 导出 `onDisable`：先把渲染开关关掉（钩子路径的钩子已注册、撤不掉，只能变成直通），再把聊天还原回来。还原读的是每张图上的 `data-st-emote-token`——**标记原文记在图上**，而不是从设置里反推，所以还原不依赖表情包还处于启用状态。还原分两段：先用客户的源文本重排（有源文本的，块级图能回到模型写它的段落里），再把剩下的图就地换回标记（流式预览这类没有源文本的）。

**Consequences**：`STICKER_CLASS` 不再是字面量，改基类名时两个路径会一起动；图上多了一个 `data-st-emote-token`，它属于"两条路径同一组 `data-*`"的一部分，不是某一侧的私有字段。`adapter/rendering.js` 的 DOM 后处理整体被 `domPathInstalled && isRenderingEnabled()` 门控：前者让一个不区分路径的调用方（改设置、重新启用）不会在钩子路径的客户端上跑 DOM 遍历，后者保证**关闭扩展后事件仍然不会再把图插回来**——事件订阅活过 `onDisable`（客户端不刷新页面，而退订要记住每个监听器），所以闸门必须在遍历里面而不是订阅外面。钩子安装失败时回落 DOM 路径：客户有 `addHook` 不等于签名相同，而 DOM 路径在 1.15.0 起的每个版本都能用。

# 表情图片存在 ST 用户数据目录里的既有特性目录下

本扩展不新增服务端代码，图片一律经 ST 自带的上传接口写入用户数据目录；而 ST 提供的上传接口全都落在别的特性自己的目录里（Data Bank 附件、画廊、背景库……），所以"扩展自有目录"这个理想做不到，只能挑污染最小的一个，并用文件名前缀区分归属。元数据（表情包 / 表情 / 全局启停）存在扩展设置里，角色层启停写进角色卡，聊天层启停写进聊天元数据。

**Considered Options**：新增服务端代码或插件提供专用目录（被否，见 ADR-0001）；图片以 data URI 内嵌进扩展设置（被否：会撑爆 ST 的设置文件，且官方文档明确反对把大图放进扩展设置）；图片放浏览器侧存储（被否：换浏览器就丢图，违反"跨设备可见"这条需求）。

**Consequences**：删除操作必须严格限定在"本扩展创建的文件"范围内；缺图是常态（配置跨设备、图片不跟），因此缺图必须按未命中处理并允许重新指定图片。

## 追加：归属靠文件名前缀判定（票 06）

归属判定因此有了唯一依据：**目录 + 前缀**。所有上传的文件都写成 `user/images/st-emote/st-emote-<stickerId>.<ext>`，`isOwnImagePath`（`core/image-rules.js`）只认这一种形状，删除路径一律先过它。这条同时解释了两件事：为什么文件名里要塞进 sticker id（一张图只被一个表情用，id 天然唯一，也就没有共享引用），以及为什么导入别人给的包时每张表情都要重新上传（外来文件不满足这个形状，不能直接落进这个目录）。

**一个图片只被一个表情使用**这条不变量没有单独的实现，是这条命名的推论：文件名由表情 id 决定，所以两个表情不可能指向同一个文件；替换图片时旧文件随之删除，删除表情时新文件随之删除。

## 追加：导出包的格式（票 06）

一个表情包导出成单个 zip：`st-emote.json`（**包清单**）+ `images/`（图片）。包清单里每张表情只有**标签、描述、投放方式覆盖**，加上图片的**来源**——本地文件写 `file`（压缩包内的路径），外链写 `url`。包清单刻意**不记录**本地存储路径：那个路径是本机的地址，换一台机器就没有意义，记下来反而会让导入方以为可以直接使用。（「包清单」是导出包里的那份元数据，与 `CONTEXT.md` 里的**清单 / Listing**——宏 `{{st-emote}}` 的输出——是两个词，不要混用。）

包清单的校验全在 `core/manifest.js`（`parseManifest` + `planImport`），因为压缩包是**别人构造的输入**：格式标记、版本、包名合法性、字段约束、重复标签、`file` 不得越出 `images/`（`isSafeArchivePath`），以及**每张图片的格式与体积**——一条不过整个包就拒收，不做部分导入。最后这一条是关键：导入是让任意 zip 里的字节进入图片目录的通道，如果它绕过 `core/image-rules.js` 的四条格式与 5MB 上限，那这套规则就等于只管手动上传。压缩包本身由 `adapter/archive.js` 用 ST 自带的 `/lib/jszip.min.js` 读写，**不新增任何运行时依赖**（测试用的是 devDependency `jszip`，所以没有本机 ST checkout 也能跑）。
